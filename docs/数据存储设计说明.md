# 智能仓储管理系统 —— 数据存储与容量设计说明

> 对应需求文档 **2.5 数据管理能力要求**、**3.1 设备**、**3.2 支撑软件**
> 本文的数字全部来自实测脚本 `tools/benchmark_scale.py`，不是估算。答辩时可直接演示。
>
> **2026-11-03 复测备注**：在 macOS 27 / Apple Silicon 上重跑标准场景，
> 数据量仍为 772,470 行 / 59.7 MB，批量导入 5.6 s，
> 最慢查询（全量 319,494 条明细）248 ms。原表中的 Windows 数字保留作为对照。

---

## 一、结论先讲

**SQLite 存三年经营数据完全没问题，而且绰绰有余。**

| 项目 | 实测结果 | 需求上限 | 余量 |
|---|---|---|---|
| 数据跨度 | 3 年（1095 天） | ≥3 年 | 达标 |
| 数据总量 | 77.2 万行 | — | — |
| 数据库文件 | **59.7 MB** | 文档预估 <2 GB | **仅占 3%** |
| 最慢的一条分析查询 | **432 ms** | ≤15 s | 快 34 倍 |

也就是说，按需求文档里"总量不超过 2GB"的预估，三年数据只用了不到三十分之一。
**容量根本不是这个项目的瓶颈，不要在这上面花时间。**

## 二、实测数据（标准场景）

测试参数：300 个 SKU、日均 100 张小票、跨期 1095 天（2023-10 ~ 2026-10）。

| 表 | 行数 | 说明 |
|---|---|---|
| `products` | 300 | SKU 商品档案 |
| `transactions` | 124,476 | 交易头（一张小票一行） |
| `transaction_items` | 319,494 | 交易明细 |
| `inventory` | 328,500 | 库存快照（300 SKU × 1095 天） |
| **合计** | **772,470** | **数据库文件 59.7 MB** |

批量导入 77 万行耗时 **19.2 秒**（一次性导入三年历史数据，之后每天增量只导当天数据）。

### 查询性能

| 查询场景 | 耗时 | 对应功能 | 结论 |
|---|---|---|---|
| 购物篮明细提取（近 90 天） | 42 ms | Apriori 关联分析 | ✅ |
| 单 SKU 日销量序列（近 90 天） | 15 ms | 补货预测 | ✅ |
| ABC 销售额汇总（近 365 天） | 103 ms | 畅销/滞销判定 | ✅ |
| 全周期库存快照聚合 | 39 ms | 滞销判定 | ✅ |
| 全量销售明细拉取（**无窗口**，最坏情况） | 432 ms | — | ✅ |

**即使是"不分时间窗口、把三年明细全部拉进内存"这种最粗暴的写法，也只有 0.43 秒。**
需求 1.1 要求的"较大数据集≤15s"有巨大余量。

### 压力场景（大型门店，验证容量上限）

测试参数：800 个 SKU、日均 300 张小票、跨期 1095 天。

| 项目 | 结果 |
|---|---|
| 数据总量 | **2,209,265 行**（220 万行） |
| 数据库文件 | **170.4 MB** |
| 最慢查询（全量拉取 96 万条明细） | **1,337 ms** |
| 日常分析查询（购物篮 / ABC / 库存） | 22 ~ 364 ms |

**即使门店规模是标准场景的 3 倍，三年数据也只有 170 MB，所有查询仍在 1.5 秒内。**
这说明 SQLite 方案对本项目有充分的容量余量。

## 三、三年数据量下必须注意的两个性能坑（已解决）

这两个问题在小数据（120 天）下完全看不出来，只有在三年量级才会暴露。
**这是本项目数据层最值得写进设计文档的部分。**

### 坑 1：没有统计信息，SQLite 会选错执行计划

ABC 销售额汇总查询，未优化前耗时 **6640 ms**——虽然还没超 15 秒，但已经明显卡顿。

原因是 SQLite 在没有统计信息时，选择了"全表扫描 `transaction_items`（32 万行），
再逐行回查 `transactions`"的糟糕计划，而不是"先用 `ts` 索引筛出一年内的订单，
再反查明细"。

执行一次 `ANALYZE` 后，耗时降到 **112 ms，快了 59 倍**。

> **落地做法**：`app/db/schema.py` 里已提供 `analyze()` 函数，
> 并且在 `insert_sales()` 单批超过 2000 行时会自动执行。
> 大批量导入历史数据后务必保证它跑过一次。

### 坑 2：库存表聚合要回表

`SELECT sku_id, AVG(stock_qty) FROM inventory GROUP BY sku_id`，
在 32 万行库存快照上耗时 **2174 ms**。问题在于主键索引 `(sku_id, snapshot_date)`
里没有 `stock_qty`，每行都要回主表取值。

加一个覆盖索引 `(sku_id, stock_qty)` 后降到 **36 ms，快了 60 倍**。

> **落地做法**：`idx_inv_sku_stock` 已写进建表语句。

### 优化前后对比（总表）

| 查询 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| ABC 销售额汇总 | 6,640 ms | 103 ms | **64×** |
| 全周期库存聚合 | 2,174 ms | 39 ms | **56×** |

## 四、表结构设计

七张表，对应需求 2.5 要求的"销售小票记录、SKU 商品档案、库存记录、分析报告"四类数据，
外加配置表与实时库存流水表。

```
products            商品档案     sku_id / sku_name / category / cost / price / updated_at
transactions        交易头       order_id / ts / total_amount
transaction_items   交易明细     order_id / sku_id / qty / unit_price
inventory           库存快照     sku_id / snapshot_date / stock_qty / cost
inventory_events    库存流水     id / sku_id / ts / action / delta / stock_after / source
reports             历史报告     report_id / report_type / generated_at / content
config              业务参数     key / value
```

### 四个设计要点

1. **交易拆成 `transactions` + `transaction_items` 两张表。**
   一张小票是一行头 + 若干行明细。购物篮分析要按 `order_id` 把同一篮子里的商品聚合，
   这个拆分是必须的。

2. **数据是幂等的。** 同一订单重复导入不会产生重复明细——
   明细表上有唯一索引 `(order_id, sku_id)`，配合 `INSERT OR REPLACE`。
   **这一点对三年数据很重要**：如果重复导入三年历史，非幂等的写法会让库凭空膨胀一倍。

3. **实时库存流水**：`inventory_events` 按秒记录卖出/补货/建档/调整，
   与 `inventory` 最新快照、`transactions` 销售流水在同一事务中写入。
4. **时间字段统一存 ISO 文本**（`2026-10-13 14:32`）。
   SQLite 没原生日期类型，ISO 格式的文本可以直接用字符串比较做时间范围筛选，
   配合 `ts` 索引效率很高，也方便直接用 `substr(ts,1,10)` 取日期分组。

### 索引清单

| 索引 | 表 | 作用 |
|---|---|---|
| `idx_tx_ts` | transactions | 按时间窗口筛选（所有分析都要用） |
| `idx_item_order` | transaction_items | 按订单聚合购物篮 |
| `idx_item_sku` | transaction_items | 按 SKU 汇总销量 |
| `uq_item_order_sku` | transaction_items | 唯一约束，保证导入幂等 |
| `idx_inv_sku_stock` | inventory | 库存覆盖索引（见坑 2） |

索引用多了会拖慢写入、占空间，所以只建这五个，都是被实际查询用到的。
**不要盲目给每一列都加索引。**

## 五、存储策略：怎么装下三年，又不用天天等

### 5.1 单文件，拷走即备份

整个数据库就是一个 `data/app.db` 文件，没有服务进程、没有账号权限。
`VACUUM INTO` 可以把库直接导出成一个备份文件（对应需求 2.5「支持导出历史数据备份」），
三年数据也就 60 MB，U 盘随便拷。

### 5.2 分层保留策略

不是所有数据都值得按同样的粒度保存三年：

| 数据 | 保留策略 | 理由 |
|---|---|---|
| 交易头 / 明细 | **全量保留 3 年+** | 占用极小（60 MB），且关联分析、同比都依赖长周期数据 |
| 库存快照 | 全量保留；可降为按周留痕 | 快照是 300 SKU × 1095 天 = 32.8 万行，是最大的一张表。如果库再大，可改成**每周存一次**，容量直接降到 1/7，对补货分析精度影响很小 |
| 历史报告 | 按需清理 | 纯文本，量小，但旧的周报参考价值低 |

### 5.3 分析时一定要加时间窗口

**存三年 ≠ 每次分析都读三年。** 不同分析适合的窗口不同：

| 分析 | 建议窗口 | 理由 |
|---|---|---|
| 购物篮关联（Apriori） | 近 90 天 | 越近的数据越能反映当前连带关系；三个月足够积累上万张小票 |
| 补货预测 | 近 30～90 天 | 日均销量和波动率只需近期数据 |
| ABC 畅销/滞销 | 近 90～365 天 | 太短会把季节性商品误判 |
| 换季趋势 / 同比 | 近 2～3 年 | 唯一需要跨年的分析，也是保留三年数据的**主要理由** |

> 结论：**保留三年数据的真正价值在于"换季趋势和同比分析"**，
> 而不是让每个查询都去扫三年。日常分析走 90 天窗口，几百毫秒就出结果。

## 六、可直接写进需求文档的文本

### 6.1 「2.5 数据管理能力要求」补充段

> 系统采用 SQLite 3 嵌入式数据库，以单文件形式存储全部业务数据，无需安装独立数据库服务。
> 数据保存周期**不低于 3 年**，以支持跨年度同比分析与季节性趋势挖掘。
> 经实测，在 300 个 SKU、日均 100 笔交易的标准场景下，三年累计产生约 77 万条记录，
> 数据库文件约 60 MB，远低于磁盘容量上限；最复杂的分析查询响应时间低于 0.5 秒，
> 满足性能指标要求。系统支持将数据库整体导出为备份文件，
> 单文件拷贝即可完成迁移与归档。

### 6.2 「3.1 设备」存储项修订

> 硬盘空间：程序与运行库约 500 MB，本地大模型文件约 3 GB，
> 三年经营数据约 **200 MB**（按 300 SKU 规模实测 59.7 MB；按 800 SKU、
> 日均 300 笔交易的大型门店实测 170.4 MB），合计建议预留 **10 GB** 可用空间。

### 6.3 「3.2 支撑软件」数据库项修订

> 数据库管理系统：SQLite 3（通过 Python 标准库 `sqlite3` 模块调用，无需单独安装）。
> 采用 WAL 日志模式，支持读写并发；通过 `ANALYZE` 维护查询统计信息，
> 并以覆盖索引优化聚合查询性能。

## 七、怎么自己复现这份实测结果

```bash
cd Intelligent_Warehousing
.venv/Scripts/python.exe tools/benchmark_scale.py
```

可调参数：

```bash
# 默认：三年 / 300 SKU / 日均 100 张小票
python tools/benchmark_scale.py

# 压力场景：大型门店，800 SKU / 日均 300 张小票
python tools/benchmark_scale.py --sku 800 --orders 300

# 试算更长的保留周期
python tools/benchmark_scale.py --days 1825   # 五年
```

脚本会用独立文件 `data/bench.db` 测试，**不会影响正式的 `data/app.db`**。
测完直接删掉 `data/bench.db` 即可。

> 注意：`tools/make_fake_data.py`（120 天小而精的假数据，用于验证算法正确性）
> 和 `tools/benchmark_scale.py`（三年大而糙的数据，用于验证容量性能）是**两个不同用途**的脚本，
> 不要混用。前者你**知道正确答案**，能检查算法算得对不对；后者只用来测容量和速度。
